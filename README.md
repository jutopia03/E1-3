# Mini NPU Simulator

입력 패턴과 필터를 같은 위치끼리 곱하고 모두 더하는 **MAC(Multiply-Accumulate) 연산**으로
패턴이 십자가(Cross)인지 X인지 판정하는 Python 콘솔 프로그램입니다.
외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `os`, `sys`, `unicodedata`)만 사용합니다.

## 실행 방법

```bash
python main.py                            # data.json(main.py와 같은 폴더) 사용
python main.py samples/data_broken.json   # 의도적 오류 데이터로 모드 2 실행
```

실행 후 모드를 선택합니다.

| 번호 | 모드 | 내용 |
|---|---|---|
| 1 | 사용자 입력 (3×3) | 필터 A, B와 패턴을 한 줄씩(공백 구분) 입력 → 점수 / 판정(A·B·판정 불가) / 성능 출력. 1행에 `cross` 또는 `x`를 입력하면 해당 패턴 자동 생성 |
| 2 | data.json 분석 | 필터 로드 → 패턴별 판정과 PASS/FAIL → 크기별 성능 표 → 결과 요약 |
| 3 | 패턴 생성기 (보너스) | 크기 N 입력 → N×N Cross / X 패턴 생성, 판정, 성능 측정 |

- 실행 환경: Python 3.14.0, Windows (PowerShell). Python 3.8 이상에서 동작하도록 작성
- 데이터 파일: `data.json`은 `main.py`와 같은 폴더에 있어야 합니다. 인자로 다른 경로를 줄 수도 있습니다.

## 구현 요약

### 데이터 구조
n×n 배열을 리스트의 리스트로 저장합니다. `create_matrix`, `get_value`, `set_value`로 특정 위치의 값을 읽고 씁니다.
`validate_matrix(m, n)`은 n×n 숫자 배열인지 검사합니다. 예외를 던지지 않고 **문제 원인을 문자열로 반환**하므로, 호출한 쪽에서 케이스 단위 FAIL로 처리할 수 있습니다.

### 라벨 정규화
외부 데이터는 같은 의미를 여러 표기로 씁니다. expected 값은 `'+'`와 `'x'`, 필터 키는 `'cross'`와 `'x'`입니다.
이 표기들을 비교 전에 하나의 표준 라벨 `Cross`/`X`로 바꿉니다(`normalize_label`, 앞뒤 공백과 대소문자 무시).
정규화하지 않으면 판정 결과 `"Cross"`와 expected `"+"`를 문자열로 비교하게 됩니다. 그러면 판정이 맞아도 FAIL이 됩니다.
알 수 없는 표기는 `None`을 반환하고, 그 케이스는 "알 수 없는 expected 값"으로 FAIL 처리합니다.

### MAC 연산
`mac(pattern, filt)`는 이중 for문으로 `total += pattern[i][j] * filt[i][j]`를 N×N번 반복합니다. NumPy는 사용하지 않습니다.

### 동점 처리 정책 (epsilon)
`abs(score_a - score_b) < 1e-9`이면 동점으로 보고 `UNDECIDED`(모드 1에서는 "판정 불가")로 판정합니다.
UNDECIDED는 expected(Cross/X)와 같을 수 없으므로 FAIL입니다.

### 모드 2 검증 순서 (`analyze_pattern`)
1. 패턴 키 `size_{N}_{idx}`에서 N 추출 (형식이 틀리면 FAIL)
2. expected 라벨 정규화 (알 수 없는 값이면 FAIL)
3. `size_N` 필터 존재 여부 확인 (없으면 FAIL)
4. 패턴이 N×N 숫자 배열인지 확인 (크기나 형식이 틀리면 FAIL)
5. MAC → 판정 → expected와 비교

어느 단계에서 걸려도 예외 없이 사유와 함께 FAIL을 반환하므로, 프로그램이 중간에 종료되지 않습니다.

### 2. 실패 원인 분석

실패 원인은 세 가지로 나눠 점검했습니다.

| 구분 | 점검 내용 | 결론 |
|---|---|---|
| 데이터/스키마 문제 | 키 형식, 라벨 표기, 필터와 패턴의 크기 | 이상 없음. 라벨은 정규화로 처리되어 표기 차이로 생긴 FAIL은 0건 |
| 로직 문제 | 동점이 아닌 케이스 3건이 모두 PASS | MAC과 판정 로직은 정상 |
| 수치 비교 문제 | 실패 3건 모두 두 점수 차이가 약 1e-15 수준 | **실패 3건 전부의 원인** |

실패 3건은 **필터 가중치가 두 점수가 같아지도록 설계된 데이터**에서 나왔습니다.
설계상 같은 값인데 부동소수점 오차로 아주 미세하게 다르게 계산됐고, epsilon 정책이 이를 동점으로 처리해 FAIL이 된 것입니다.

- **size_5_1**
  - X 필터: 대각선 9칸이 모두 0.1이므로, X 패턴을 넣으면 0.1 × 9 = 0.9
  - Cross 필터: X 패턴과 겹치는 칸은 중앙 하나뿐이고 그 값이 0.9
  - 결과: 설계상 0.9 대 0.9
- **size_13_2**
  - Cross 필터: 십자 25칸(13 + 13 - 1)이 모두 0.3이므로, Cross 패턴을 넣으면 0.3 × 25 = 7.5
  - X 필터: 겹치는 중앙 칸의 값이 7.5
- **size_25_1**
  - X 필터: 대각선 49칸(25 + 25 - 1)이 모두 0.1이므로 0.1 × 49 = 4.9
  - Cross 필터: 겹치는 중앙 칸의 값이 4.9

**부동소수점 오차의 원인.** 0.1이나 0.3은 2진수로 정확히 표현되지 않아 근사값으로 저장됩니다.
`total += a * b`로 여러 번 누적하면 이 오차가 쌓여 `0.8999999999999999`, `7.499999999999997`처럼 됩니다.
반면 중앙 칸 하나만 곱한 쪽은 오차가 쌓이지 않아 `0.9`, `7.5` 그대로입니다.
(참고: Python 3.12 이상의 내장 `sum()`은 실수 합산 오차를 보정해서 정확히 0.9가 나옵니다. 반복문으로 직접 누적하면 위처럼 오차가 드러납니다.)

**epsilon 정책이 없었다면** `>` 비교로 아래처럼 판정됐을 것입니다.

| 케이스 | epsilon 없이 판정 | expected | 결과 |
|---|---|---|---|
| size_5_1 | Cross (0.9 > 0.8999…) | X | FAIL |
| size_13_2 | X (7.5 > 7.4999…) | Cross | FAIL |
| size_25_1 | Cross (4.9 > 4.8999…) | X | FAIL |

결과는 똑같이 FAIL입니다. 하지만 1e-15 크기의 오차로 정해진 "가짜 승자"가 나오기 때문에, 로직이 틀린 라벨을 고른 것처럼 보이게 됩니다.
epsilon 비교를 써야 원인이 "로직 오류"가 아니라 **"동점 데이터와 동점 정책에 따른 FAIL"**로 정확히 분류됩니다.
따라서 이 3건은 고쳐야 할 버그가 아니라 정책이 의도대로 동작한 결과로 보고, 필터 값이나 epsilon을 조정하지 않았습니다.

**오류 처리 검증 (`samples/data_broken.json`)**
- 넣은 오류: 행 수 부족 필터, 잘못된 필터 키, 열 수 불일치 패턴, 알 수 없는 expected(`'o'`), 문자열 값(`"1"`), 필터 없는 크기, 잘못된 패턴 키, expected 불일치
- 결과: 프로그램이 끝까지 실행되고, 8개 중 7개가 서로 다른 사유로 FAIL 처리됐습니다.

### 3. 성능 분석 (평균 / 10회, Python 3.14.0, Windows)

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | 곱셈 1회당 시간(µs) |
|---|---|---|---|
| 3×3 | 0.0024 | 9 | 0.267 |
| 5×5 | 0.0046 | 25 | 0.184 |
| 13×13 | 0.0244 | 169 | 0.144 |
| 25×25 | 0.0771 | 625 | 0.123 |

- **측정 방법:** I/O를 빼고 MAC 함수 호출 구간만 쟀습니다. 한 번 실행은 너무 짧아 타이머 오차가 크므로, 10회 전체를 `time.perf_counter()`로 한 번에 잰 뒤 10으로 나눴습니다. 측정 전 워밍업 1회를 했고, 모든 크기에서 생성기로 만든 같은 형태의 Cross 패턴과 필터를 사용했습니다.

### 4. 시간 복잡도 O(N²) 분석

- **연산 횟수:** MAC은 N×N 배열의 모든 칸에 곱셈 1번과 덧셈 1번을 하므로 연산 횟수가 정확히 N²입니다. 이중 for문이 각각 N번씩 돌기 때문에 시간 복잡도는 **O(N²)**입니다.
- **측정 결과에서 확인한 것:** 크기가 커질수록 시간도 함께 늘었습니다.

  | 구간 | 연산 횟수 증가 | 시간 증가 |
  |---|---|---|
  | 5×5 → 13×13 | 6.8배 (25 → 169) | 5.3배 |
  | 13×13 → 25×25 | 3.7배 (169 → 625) | 3.2배 |

- **시간 증가가 N² 증가보다 작은 이유:** 함수 호출이나 `range` 객체 생성처럼 N과 상관없이 매번 드는 고정 비용이 있기 때문입니다. 실제 시간은 `a·N² + b`(b는 고정 비용) 꼴입니다.
  - N이 작으면 b의 비중이 커서 곱셈 1회당 시간이 크게 나옵니다. 3×3에서는 0.267µs입니다.
  - N이 커지면 b가 무시할 만큼 작아져서, 곱셈 1회당 시간이 일정한 값(약 0.12µs)으로 수렴합니다.
  - 이 수렴이 시간이 N²에 비례한다는 근거입니다.
- **AI 연산과의 연결:** 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용합니다. N이 10배가 되면 연산이 100배가 되므로, CPU처럼 하나씩 순서대로 처리하는 방식으로는 감당이 어렵습니다. 수천 개의 MAC을 동시에 처리하는 NPU가 필요한 이유입니다.

### 5. 보너스: 2D vs 1D 배열 MAC 비교 (동일 입력, 동일 반복 10회)

| 크기 | 2D(ms) | 1D(ms) | 2D/1D |
|---|---|---|---|
| 3×3 | 0.0024 | 0.0015 | 1.62x |
| 5×5 | 0.0046 | 0.0028 | 1.66x |
| 13×13 | 0.0244 | 0.0147 | 1.66x |
| 25×25 | 0.0771 | 0.0432 | 1.79x |

- **1D 버전이 1.6~1.8배 빠른 이유:** 2D 버전은 `pattern[i][j]`를 읽을 때마다 행 리스트를 꺼내고, 그 안에서 다시 값을 꺼내는 인덱싱을 두 번 합니다. `flatten`으로 펼친 1D 버전은 `pattern[k]` 한 번이면 됩니다. 바깥 루프도 없어져서 루프 관리 비용도 줄어듭니다.
- **복잡도는 그대로입니다:** 곱셈 횟수는 둘 다 N²이므로 시간 복잡도는 똑같이 O(N²)이고, 줄어든 것은 비례 상수 a입니다.
- **주의할 점:** 배열을 펼치는 `flatten` 자체에도 O(N²) 비용이 듭니다. 같은 필터로 여러 패턴을 판정할 때처럼, 한 번 펼쳐 여러 번 재사용하는 경우에만 이득입니다.
